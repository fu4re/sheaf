# SPIKE-T1 — Ghost-механика на CALL + аппендиксы TCG-005 (инженер)

**Проект:** Loop-based TCG. **Контекст спайка:** до вложений в доказательство теоремы A3b проверяем на одном сквозном примере, собирается ли R/G-композиция над EVM. Эта задача — фундамент спайка: рабочий ghost-монитор.
**Стенд:** C9-стенд (kontrol 1.0.255 / K v7.1.337 / KEVM 1.0.678, пиннован) + vendored fork из C9-Q4 (1 строка: `<callCounter>` в evm.md). Версии/хеши/логи — как в report.md.
**Блокирует:** SPIKE-T3. **Параллельно:** SPIKE-T2 (независима).

---

**Контекст (2 абзаца для исполнителя):** В C9-Q4 показано: ghost-ячейку можно объявить только форком evm.md (1 строка), ячейка констрейнится в claims. НЕ показано главное: **инкремент ячейки при исполнении CALL-семейства опкодов**. В K правило переписывает конфигурацию, матчась на голову `<k>`; правило-инкремент матчится на ту же голову, что штатное CALL-правило KEVM → конкуренция правил (приоритеты — ровно тот механизм, из-за которого мы не доверяем CSE-summary). Вопрос задачи: существует ли механика инкремента, не переписывающая штатные правила, и если нет — каков реальный объём правки.

Ответ определяет цену леммы A5 (прозрачность инструментации): «добавленная ячейка + свои правила» доказывается легко; «изменённые правила семантики» — качественно дороже. Попутно закрываем два дешёвых аппендикса TCG-005 §6 — они нужны для базы индукции A3a и junction-механики, стенд тот же.

**Q1 — Инкремент на CALL: механика [ядро]**

Испробовать по возрастанию инвазивности, фиксируя провал каждого уровня:
- (i) правило в внешнем модуле с более высоким приоритетом, инкрементящее `<callCounter>` и возвращающее управление штатному CALL (анти-паттерн: бесконечный цикл самоприменения — зафиксировать, как предотвращён);
- (ii) правка самих CALL-правил в форке: добавить обновление ячейки в RHS. Посчитать точно: сколько правил тронуто (CALL/CALLCODE/DELEGATECALL/STATICCALL/CREATE/CREATE2), диff построчно;
- (iii) если есть иной штатный механизм K (strictness/hooks/`#next`-инструментация) — описать.

Обязательная проверка на каждом уровне: **штатное поведение не сломано** — существующий KEVM-тест/спек из дерева проходит на форке (указать какой).

**Формат вердикта:** `без правки штатных правил: возможно (механизм) | только правка (N правил, diff приложен)` + прогон.

**Критерий решения:** (i)/(iii) → A5 в дешёвой форме, форк остаётся минимальным. (ii) → A5 формулируется про изменённые правила; N и diff — вход для оценки.

**Q2 — Сквозной toy-прогон + поведение при REVERT [подтверждение]**

Контракт A вызывает контракт B (Foundry-тест на стенде). Claim: после исполнения `<callCounter>` увеличился ровно на число внешних вызовов (константа для toy). Прогнать kprove/kontrol на форке. Это первый в проекте прогон, где trace-факт («был вызов») выражен в Post через ghost.

Дополнительно — **персистентность через REVERT** (критично для T2): вариант, где B ревертит (A ловит через try/catch либо низкоуровневый call). Проверить: откатывается ли ghost-ячейка штатным механизмом отката KEVM вместе с account-state или переживает revert. Ожидаемо (ячейка вне account-substate) — переживает; «ожидаемо» ≠ факт. Если откатывается — монитор слеп к атакам за try/catch, интерфейс монитора для T2/T3 меняется (нужен незатрагиваемый откатом носитель).

**Формат:** PROVED/FAILED + спек + лог; для revert-варианта — значение ячейки до/после отката.

**Q3 — Аппендикс TCG-005 §6.1: goal-as-own-circularity**

Проверить: регистрирует ли kprove доказываемую цель как собственную circularity (тогда C≠∅ у листьев ⟹ ⊨⁺ бесплатно — база индукции A3a). Дизайн: claim, замыкание которого требует применения самого себя после ≥1 шага (классическая loop-спека: счётчик до нуля). Если PROVED — цель была применима как circularity; отрицательный контроль: тот же claim при заведомо недостижимом самоприменении.

**Формат вердикта:** `цель ∈ C (самоприменима после шага) | нет` + лог момента применения.

**Q4 — Аппендикс TCG-005 §6.2: consequence-механика стыка**

Показать junction БЕЗ trusted-леммы: доказательство родительского claim'а, где промежуточная конфигурация удовлетворяет Post_i, и переход к Pre_j происходит **импликацией** (subsumption/simplification), не применением правила. Минимальная пара спеков; зафиксировать, чем в логах отличается consequence-переход от применения trusted-правила (нам нужен различитель для шага 4 протокола).

**Формат вердикта:** `механика продемонстрирована (как выглядит в логах) | не удалось (что мешает)`.
