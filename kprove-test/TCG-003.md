## 1. Собранные факты (проверено, с источниками)
 
Все гипотезы ниже построены на этих фактах, а не на памяти.
 
### 1.1 Kontrol / KEVM
 
- **Kontrol активен**, v1.0.241 (июнь 2026). BSD-3. Источник: github.com/runtimeverification/kontrol
- **CSE (Compositional Symbolic Execution)** существует, флаг `--cse`. Механика: функции анализируются изолированно в абстрактном символьном окружении → результат сохраняется как **K-правила** (summaries) → при повторном вызове применяется summary вместо повторного исполнения → **summary вставляются с более высоким приоритетом**, иначе инструмент исследует все пути обычным символьным исполнением. Порядок bottom-up по графу вызовов.
- **RV называет summary артефактом:** «once generated, summaries can be used across multiple tests and even projects, or serve as verification artifacts that can be shared with the community».
- **Интерфейс = NatSpec-precondition** (`@custom:kontrol-precondition`): включается в path constraints summary; summary покрывает только ветки, где предусловия выполнены. **Статус экспериментальный**; неподдерживаемые конструкции **молча игнорируются**. Не поддерживаются: доступ к массивам/маппингам, вложенный member-access, смещения packed storage.
- **Digest-файл** (`out/digest`): `kompilation` (SHA-256 артефакта компиляции), `foundry` (хеш версии), `methods` (хеш сигнатуры + хеш контракта). Хеш метода = хеш(сигнатура, AST, storage-digest, contract-digest) — **якорь на источник, не на семантику**.
- **Trusted claims в K:** доказанный claim помечается атрибутом `trusted`; kprove имеет флаг `--trusted`. Разработчики K прямо предупреждают: модификация trusted-claims **позволяет пользователю сделать unsound-вещи**, итоговый прогон должен быть выполнен с начала; **trusted claims не должны применяться как circularity-правила**.
  Источник: github.com/kframework/kore/issues/1277, k/CHANGELOG.md
- **Proof generation в K:** proof objects как сертификаты для K-генерируемых интерпретаторов и верификаторов; matching logic proof checker (MLPC) на Metamath, TCB ~250 строк. **Демонстрации: ERE и IMP. Применимость к KEVM-масштабу НЕ подтверждена.** Признанная проблема размера: proof может быть миллионы строк, повторная проверка неэффективна → предложен zk-вектор.
  Источник: research.runtimeverification.com/Logic/, CAV'21 (Chen et al.), ITP_ML
 
### 1.2 Certora
 
- **Prover открыт** (github.com/Certora/CertoraProver, © 2025 Certora Ltd), 7+ лет разработки, заявлено $100B+ TVL, 70k+ правил.
- **Архитектура:** EVM-байткод → декомпилятор → **TAC** (three-address code) → статический анализ → VC-генератор → off-the-shelf SMT-солверы.
- **Unsoundness как продуктовая фича:** «rich set of features for approximating difficult-to-verify code, giving users fine-grained tools for trading soundness for completeness»; «we check that the method's summary is a correct approximation of the actual method definition. In practice, it is sometimes useful to **omit the second check** to give rule writers maximum flexibility».
- **Семантика EVM имплицитна** в коде декомпилятора и VC-генератора; отдельного артефакта семантики нет. Опубликованной conformance-валидации TAC-пайплайна против ethereum/tests **не найдено** (отсутствие находки ≠ отсутствие).
 
### 1.3 SMTChecker
 
- Source-уровень, движки BMC и CHC; **CHC строит нелинейные Horn-клаузы с summaries вызываемых функций** (третья дисциплина композиции). Солвер z3.
- Заявление о доверии дословно: если цель признана safe — ложных негативов нет, **«unless there is a bug in the SMTChecker»**. Сертификата нет; solc целиком в TCB.
 
### 1.4 Act / hevm (недооценённый сосед)
 
- **Act** (argotorg/act, активен): спецификации на высокоуровневом человекочитаемом языке, **доказуемо эквивалентные EVM-байткоду через hevm**; экстракция в proof assistant (Rocq); заявленное ядро замысла — **provably correct mapping from EVM bytecode to a high-level mathematical model**, встраиваемая в разные инструменты (SMT: cvc5/z3/bitwuzla; Coq; CheckMate).
- **hevm:** быстрый символьный движок для EVM-байткода, CAV 2024 (Dxo, Soos, Paraskevopoulou, Lundfall, Brockman).
- **Следствие:** идея «своё представление + сменные backend'ы» уже существует. Обязательный пункт related work, иначе φ-IR выглядит переизобретением Act.
 
### 1.5 DafnyCOMP — уточнение фактов TCG-001 §7
 
- Цифры «>58% → 3.69%, деградация 92%» **подтверждены**. Уточнение: 3.69% — среднее по 13 моделям при Pass@8 (SD 2.14%); «>58%» относится к **другим** бенчмаркам (DafnyBench/MBPP-DFY), сравнение межбенчмарковое.
- «Архитектурное, не поисковое» **подтверждено**: плато к Pass@4, прирост Pass@4→Pass@8 всего 0.8%, тогда как синтаксис растёт (+7.3%). Вывод авторов, независимо не воспроизведён.
- **РАСХОЖДЕНИЕ ВЕРСИЙ (обновить TCG-001 §7):** v1 arXiv — 300 программ, chain-based. Версия OpenReview — **400 программ: 300 chain + 100 non-chain DAG из 10 topology-шаблонов**. Важно для B1: DAG-инстансы теперь есть, бенчмарк должен покрывать оба класса.
- **Прямое подтверждение нашей рамки от авторов:** «any system requiring compositional correctness — from distributed systems protocols to **smart contract verification** — will face similar failures until models can reason about specification flow across component boundaries». Цитируемое обоснование вклада №1.

## 2. Почему CSE summary не годится как носитель доверия
 
Различие, которое всё решает: **в K rule ≠ claim.**
 
| | Summary (rule) | Claim |
|---|---|---|
| Логический статус | вносится в теорию, *применяется* | формулируется как цель, *доказывается* против теории |
| Условие корректности | неявное: «порождён доверенным прогоном» | явное: Accept от prover'а |
| Проверка третьим лицом | только полный повтор порождения | перезапуск `kprove` — штатная операция |
| Формат | внутренний KCFG/KAST, версионно-зависимый | синтаксис spec-модуля, стабильнее |
| Trace/Exit | state transformation, не носитель trace-свойств | конфигурационный уровень доступен |
| Приоритет | вставляется с приоритетом, **перекрывая** правила KEVM | ничего не перекрывает |
 
**Решение:** CSE — **U-ускоритель** (влияет только на liveness, как G и I в whitepaper). Всё, попадающее в сертификат, — claims. Это наш сквозной принцип, применённый рекурсивно к самому верификатору.
 
**Почему наивный перенос Теоремы 1 на цепочку ломается** (три причины, каждая требует посылки):
 
1. **Смена теории.** Узел `i` доказывается против `KEVM ∪ {summaryⱼ}`, а не против KEVM. Accept относительно расширенной теории ≠ Accept относительно KEVM. Нужна лемма консервативности.
2. **Приоритет правил.** Summary **перекрывают** штатные правила KEVM — это не монотонное добавление аксиом, а переопределение.
3. **Trace/Exit не композируются как Post.** `Postᵢ ⟹ Preᵢ₊₁` — о терминальной конфигурации. Trace-инвариант (реентранси) — свойство всего пути; внешний вызов внутри `bⱼ` может ре-входить в `bᵢ`, нарушая `Traceᵢ`, при локально выполненных `Traceⱼ` и `Traceᵢ`. **Композиция trace-свойств — отдельная проблема, не следствие A/G.** Самый тяжёлый и наименее осознанный узел в TCG-001.
 
**Расхождение forward A/G ↔ CSE (зафиксировать):** obligation вида `Postᵢ ⟹ Preᵢ₊₁` в Kontrol **не найдена**. CSE композирует через summary-как-правило-с-приоритетом, не через импликацию интерфейсов. Решение «forward A/G» в TCG-001 §3 принято против литературы (DafnyCOMP), а не против нашего верификатора.

## 3. Суждение о стеке (зафиксировано)
 
### Формула: `borrow the semantics, build the certificate, commoditize the prover`
 
**Отвязаться от Kontrol — да. Отвязаться от KEVM-класса валидированной семантики — нет. Строить свой prover — нет.**
 
### Анатомия стоимости
 
| Компонент | Постройка | **Поддержка** | Заимствуемо |
|---|---|---|---|
| Семантика EVM | высокая | **перманентная**: каждый хардфорк + повторная conformance-валидация | да (KEVM, hevm, Dafny-EVM, EELS) |
| Prover/движок | очень высокая | высокая | да (kprove, hevm, CHC) |
| Certificate checker | **низкая** | низкая (формат стабилен) | частично (MLPC) |
| φ-IR + композиционная дисциплина | средняя | средняя | **нет — это и есть наш вклад** |
 
**Решающий аргумент — наш собственный (TCG-001 §6):** от каталога свойств отказались, потому что это «обязательство бесконечного сопровождения, как CVE, не масштабируется». Своя семантика EVM — **то же обязательство, только тяжелее**: каждый форк меняет fee schedule, опкоды, precompiles; невалидированная семантика рушит Assumption 1 молча. KEVM-класс — единственные с опубликованной воспроизводимой валидацией против официального test suite. Это не technology moat, а **labor moat**; воспроизводить его — худшее вложение бюджета работы, все вклады которой лежат в другом слое.
 
**Второй аргумент:** наша митигация Assumption 1 — кросс-валидация против независимой семантики (§7.2 whitepaper). Своя семантика стартует с нулём кросс-валидаторов. Заимствованная — с готовой парой (KEVM ↔ Dafny-EVM ↔ hevm).
 
### Почему Certora не может быть T-ядром (принципиально, не по качеству)
 
1. **Нет семантики как отдельного артефакта** → разрушается трёхслойность whitepaper (Def 3 checker / Def 4 семантическая истина / Assumption 3 мост). Не существует объекта, против которого формулируется `→ ⊨ φ(b)`. Assumption 1 становится нефальсифицируемой.
2. **Unsoundness как фича** → смешение режимов «гарантия»/«свидетельство», запрещённое TCG-001 §3.
3. **Монолитный TCB без сертификата** → анти-пример принципа §7.2 whitepaper («малый аудируемый certificate checker предпочтительнее монолитной решающей процедуры»).
 
Наблюдение «их prover — предопределённые компоненты языка, написанные вручную» — точный диагноз: **CVL-хуки, ghosts, summaries — это семантика, размазанная по фичам**; каждая фича = ручное расширение TCB без формального якоря.
 
**Формулировка для related work:** TCG отличается от Certora не качеством движка, а тем, **где лежит семантика**.
 
### Отвергнутая дорога (закрыта осознанно)
 
Взять EELS (ethereum/execution-specs — канонический исполняемый спек, поддержка форков аутсорсится EF) и построить свой reasoning-слой. Отвергнуто: EELS — интерпретатор, не логика; символьное исполнение, инварианты, композиция строятся с нуля → возврат к стоимости «свой prover», годы до первого Accept.

## 4. Гипотезы и ноу-хау (приняты в архитектуру)
 
**H-A. Асимметрия Refute/Accept — бесплатная мультиверификаторность. [ключевое ноу-хау]**
**Контрпример самоварифицируем, доказательство — нет.** `Refute(ce)` — конкретный трейс; прогоняется на референсном клиенте (geth / execution-specs) конкретным исполнением → доверие к источнику контрпримера не нужно вообще.
Следствие: **Certora, SMTChecker, Halmos, фаззеры работают U-рефутерами** в loop'е (дёшево, параллельно, до вызова дорогого ядра); их unsoundness-флаги безвредны, потому что их Accept игнорируется. T-ядро нужно только для финального Accept.
Уточняет `Res` whitepaper: **Refute валидируется исполнением (trustless), Accept — семантикой (trusted).** Экономика loop'а меняется радикально: большинство итераций умирает на дешёвых рефутерах.
*Оговорка:* контрпример от source-level инструмента может быть false positive от абстракции (SMTChecker это признаёт) → реплей на конкретном клиенте **обязателен** до подачи в feedback, иначе генератор получает шумовой сигнал.
 
**H-B. Verifier-агностичный сертификат.** Якорь = `(hash(runtime bytecode), canonical(φ), id(semantics), hash(theory))` — **без упоминания Kontrol**. Backend'ы объявляются списком с их TCB: kprove/KEVM сегодня, hevm/Act — кандидат, MLPC — цель. Смена backend'а не инвалидирует сертификаты. Это и есть искомая независимость от решения: **не отказом от KEVM, а понижением его статуса с «архитектурной основы» до «первого T-backend'а»**.
 
**H-C. Act как форк-кандидат вместо чистого self-build.** Стартовая точка для φ-IR — не пустой лист, а Act: уже якорен к байткоду через доказательство эквивалентности, уже экстрагируется в Rocq, уже tool-neutral. Наши дельты: (a) Trace/Exit-слой (Act моделирует контракт как state transition system; выразимость реентранси — проверить, вероятный разрыв и наш вклад); (b) композиционная дисциплина + агрегатный сертификат; (c) статус N. Риск: зрелость Act (автогенерация спеков заявлена только для очень простых контрактов) — проверять руками, задача C1-класса.
 
**H-D. Certora как adversarial baseline, не ядро.** Использование: (a) U-рефутер; (b) источник негативного корпуса для evaluation §7.3 whitepaper; (c) бенчмарк-соперник для B1. Их «summaries без проверки корректности» — готовый пример для раздела о том, почему Aasm должны быть eliminated or promoted (Assumption 5).
 
**H-E. Claim-DAG как агрегатный сертификат.** Узлы — claims, рёбра — «claim j использован как trusted при доказательстве claim i». Проверка: ацикличность (исключает circular reasoning — ровно тот риск, что называет kore-issue), перезапуск с детьми-как-trusted, хеш-пиннинг теории.
 
**H-F. Стык-как-claim.** Не выносить `Postᵢ ⟹ Preᵢ₊₁` в отдельную SMT-obligation со своей семантикой сериализации. Формулировать как **subsumption-claim** в matching logic. Выгода: исчезает отдельный мост «φ-предикат → SMT-формула» на стыках; композиция живёт в одном proof system. Закрывает часть C3 бесплатно.
 
**H-G. Summary-shadowing (роль SINDI, узел C4).** Если CSE используется в контуре: каждый применённый summary обязан быть **субсумирован** экспортированным доказанным claim'ом того же loop'а. Проверка субсумпции — SMT+rewrite-сравнение силы формул (функциональность SINDI-класса). **SINDI остаётся вне T:** его вердикт оформляется как claim и передоказывается. Ответ на C4 — не вносить в T, а замкнуть выход на checker.
 
**H-H. φ-IR с обращённым статусом доверия. [главный трюк]**
Обычная ошибка — сделать красивый IR доверенным и компилировать в claims доверенным компилятором (компилятор → TCB, новый Aasm-зазор). **Обратить направление:**
- **Канонический доверенный объект = claim** (то, что реально проверяется).
- **φ-IR = пред-форма и рендеринг:** канонизированная контент-адресуемая сериализация над ячейками EVM-конфигурации, из которой генерируются (a) claim для prover'а, (b) NatSpec-preconditions для CSE-ускорения, (c) человекочитаемый рендер (**статус N**).
- **Компилятор φ-IR → claim получает статус U**, потому что H и проверяющий валидируют **claim**, а не IR. Round-trip (print-back claim → сравнение) — дешёвая перепроверка, не расширяющая TCB.
 
Согласуется с критерием статуса N (удаление рендера не ломает гарантий). Решает D5 честно: минимальная грамотность = чтение claim-синтаксиса, IR — навигация.
Побочно чинит слабость digest'а Kontrol (якорь на AST/источник): наш digest якорится на **(hash задеплоенного runtime-байткода, hash канонического claim)** — прямое усиление Assumption 4.
 
**H-I. Rely/guarantee для Trace: call-effect signatures. [кандидат в центральный вклад A3]**
Trace-инварианты не композируются конъюнкцией (§2.3). Расширить экспортируемый интерфейс с `Postᵢ` до `(Postᵢ, Effᵢ)`, где **`Effᵢ` — эффект-сигнатура**: множество допустимых внешних вызовов (адресаты/классы, value-переводы, дисциплина повторного входа). Правило в стиле rely/guarantee (Jones 1983): каждый loop *полагается* на «окружение не ре-входит вне Effᵢ» и *гарантирует* «не вызываю наружу вне Effᵢ». Глобальный trace-инвариант выводим из локальных Trace + попарной совместимости Eff; совместимость — checker-проверяемая obligation (H-F-стиль).
**Rely/guarantee над EVM-трейсами с эффект-сигнатурами** — предполагаемо отсутствует для байткод-уровня, но это оценка, не результат исчерпывающего поиска.
 
**H-J. Портируемость как побочный эффект H-H.** Tool-neutral φ-IR допускает вторую компиляцию — в Dafny-семантику EVM. Кросс-валидация против независимой семантики (наша митигация Assumption 1) становится **механической, а не ручной**. Summary-представление этого не допускает в принципе (K-специфично).
 
**H-K. Прецедент, снимающий риск «своего представления».** До Kontrol верификация на KEVM делалась именно как наборы вручную написанных reachability claims по внешним функциям (методология верификации deposit-контракта Ethereum 2.0, ERC20-спеки RV). Наш IR — не новая онтология, а канонизация и автогенерация существовавшей практики + композиционная дисциплина поверх. Снижает риск expressiveness-разрыва.

## 5. Агрегатный артефакт: TCG-бандл
 
### 5.1 Пять принципов формата
 
1. **Один корень доверия.** Идентичность сертификата = хеш MANIFEST'а; всё trust-релевантное достижимо по хеш-ссылкам. Недостижимое — не существует для гарантии.
2. **Направление ссылок кодирует статус доверия.** N-артефакты ссылаются *на* сертификат; сертификат никогда не ссылается на N. Критерий статуса N становится **механически проверяемым**: замыкание trust-корня не содержит ссылок в `nav/`. Одна команда — grep по замыканию.
3. **Только Accept-свидетельства.** Рефутеры, история итераций, сессия — вне сертификата (в `nav/` как provenance). Soundness несут только доказанные claims.
4. **Vendoring, не пиннинг.** Бандл **содержит** исходники теории (KEVM-релиз, леммы), а не только хеши: через пять лет пиннинг на удалённый репозиторий — мёртвая ссылка. Прямое требование транзитивности доверия во времени.
5. **Формат дешевле инструмента.** Структурные проверки (хеши, DAG, toposort) переимплементируемы за вечер: JSON + SHA-256. Проверяющий не обязан доверять нашему `tcg-verify` — только prover'у и семантике.
 
### 5.2 Структура
 
```
bundle/
├── MANIFEST.json            # корень: cert_version, хеш-дерево, список roots
│
├── subject/
│   ├── runtime.bin          # runtime-байткод, бит-в-бит (Assumption 4)
│   └── environment.json     # класс E: chainid, форк, fee schedule,
│                            #   constructor-args/immutables, внешний код
├── spec/
│   ├── claims/<h>.k         # канонические claims, контент-адресация
│   ├── interfaces.json      # per-loop: (Preᵢ, Postᵢ, Effᵢ, Exitᵢ) → ссылки на claims
│   └── graph.json           # DAG: узлы=claims, рёбра=trusted-использование,
│                            #   роли: loop | junction | subsumption; помечены roots
├── theory/
│   ├── semantics/           # vendored KEVM-релиз (исходники)
│   ├── lemmas/              # проектные леммы (каждая — claim или помечена Aasm)
│   └── toolchain.lock       # версии kprove/солверов, хеши бинарей, seeds, timeouts
│
├── evidence/
│   ├── replay/<h>.json      # v1: точная инвокация prover'а на claim h,
│   │                        #   children-as-trusted, ожидаемый Accept, ресурсы
│   └── proofs/<h>.mm        # v2: proof objects (Metamath), тот же ключ h
│
├── assumptions/
│   ├── trust-manifest.json  # A1–A7 + trusted-claim-discipline: статус каждой
│   │                        #   (validated / vendored / requires-verifier-action)
│   ├── annotations.json     # Aasm-леджер: каждый факт (storage layout и т.п.)
│   │                        #   → либо ссылка на перепроверку, либо явный вход в T
│   └── oracle-record.json   # подпись H: «принят набор root-claims {h₁..hₙ}», дата
│
└── nav/                     # СТАТУС N: вне хеш-дерева MANIFEST
    ├── report.md            # человекочитаемый пересказ
    └── session/             # provenance: итерации, Refute-история, промпты
```
 
### 5.3 Ключевые проектные решения
 
**Единственная дисциплина корня.** Ответ на «что доказывает вся цепочка» — **один объект**, не свойство графа. Гарантия композита = **множество root-claims**, каждый доказан с использованием loop-claims как trusted-лемм; стыки (`Postᵢ ⟹ Preᵢ₊₁` как subsumption-claims) — внутренние узлы DAG. Для контракта с k внешними функциями roots = k claims (forest с общими поддеревьями). Проверяющий, спрашивающий «что мне гарантировано», читает **ровно roots** — не граф.
**Это фиксирует D1: H валидирует roots (+ выборочно интерфейсы), не каждый φᵢ.**
 
**Interfaces.json — носитель композиции, claims — носитель доказательства.** `(Preᵢ, Postᵢ, Effᵢ, Exitᵢ)` — декларация; каждый элемент компилируется в claim (обращённый статус доверия, H-H). `Effᵢ` живёт здесь же — задел под A3 для Trace-композиции.
 
**Trust-manifest — материализация Assumptions.** Whitepaper держит A1–A7 в тексте; бандл делает их **полем данных** с тремя статусами:
- `vendored` — A1: семантика в комплекте + ссылка на conformance-результат
- `machine-checkable` — A4: инструкция сверки hash(runtime.bin) с on-chain
- `verifier-action-required` — A7 → семантический зазор: «прочитайте roots»
 
Второй неформальный зазор (φ→N) представлен тривиально: **nav/ вне хеш-дерева — его недостоверность конструктивна, не декларативна.**
 
**Oracle-record.** Assumption 7 нельзя формализовать, но можно **датировать и атрибутировать**: подписанное заявление сессионного H о принятии roots. Внешний проверяющий ему не доверяет (его чтение roots заменяет), но запись делает транзитивность доверия во времени **аудируемой** — видно, кто и что принял в момент t.
 
### 5.4 Что артефакт переносит и что нет
 
- **Переносит полностью, без доверия к автору/LLM/сессии:** механическую часть `b ⊨ {φᵢ}` + композиционную структуру.
- **НЕ переносит:** семантическую часть — «roots выражают нужное свойство». Требует, чтобы проверяющий сам прочитал и принял roots. Неустранимо (§2.1 whitepaper).

## 6. Протокол проверяющего (`git clone` → гарантия)
 
Строго упорядочен; провал любого шага = **отказ сертификата** (консервативно).
 
| # | Шаг | Содержание | Цена |
|---|-----|-----------|------|
| 1 | **Целостность** | пересчёт хеш-дерева от MANIFEST | секунды |
| 2 | **Идентичность (A4)** | `keccak(runtime.bin)` == extcodehash on-chain; конструктор/immutables по environment.json | секунды |
| 3 | **Теория** | сборка vendored-семантики; layout-перепроверка Aasm-леджера против runtime.bin (**узел C2**) | минуты |
| 4 | **Граф** | ацикличность; замкнутость (каждый trusted-claim в evidence узла i — доказанный узел j с ребром i→j); полнота стыков (для каждой композируемой пары есть junction-узел); достижимость roots | минуты |
| 5 | **Replay (v1)** | топологический порядок; для каждого узла — пиннованная инвокация prover'а, children as trusted; ожидается Accept. **Unknown = отказ** | **часы CPU** |
| 6 | **Семантический шаг** | чтение roots. Единственное место, где нужна формальная грамотность (**D5**) — ограничена корнями, не графом, не кодом, не сессией | человеческий |
 
**Честная переформулировка вклада №3:** не «проверяющий восстанавливает доверие за минуту», а «**за перезапуск, но без онбординга в код и без доверия к автору**». Всё ещё нетривиальный вклад против статус-кво (аудит = чтение кода).

## 7. Эволюция v1 → v2
 
Единственное различие — содержимое `evidence/`: replay-скрипты → proof objects (`proofs/<h>.mm`), проверяемые MLPC вместо перезапуска prover'а.
 
**Скелет (graph.json, claims, interfaces, assumptions) не меняется** — главный аргумент строить формат сейчас, не дожидаясь зрелости proof generation для KEVM.
 
| | v1 (replay) | v2 (proof-carrying) |
|---|---|---|
| Шаг 5 протокола | часы CPU | минуты |
| TCB проверки | prover + солверы | checker ~250 строк |
| Готовность | **сегодня** | не подтверждена для KEVM |
 
**Verifier-агностичность в том же месте:** третий тип evidence (`hevm-replay`, `smt-cert`) добавляется **без ревизии формата**; MANIFEST декларирует, каким типом evidence покрыт каждый узел, и проверяющий сам решает, чей Accept принимает.

## 8. Известные слабости формата (названы, не спрятаны)
 
1. **Недетерминизм солверов.** Replay может дать Unknown на другом железе при том же seed/timeout. Митигация: retry-политика в toolchain.lock, запас по timeout. Честное ограничение v1 и главный довод за v2. **Отказ по Unknown остаётся консервативным — ложных Accept не возникает.**
2. **Vendoring ≠ воспроизводимая сборка.** Сборка K-тулчейна пятилетней давности на новой ОС — реальный риск. Паллиатив: контейнер-образ приложением к бандлу (**сам образ вне trust-корня**: доверять надо исходникам, образ — удобство).
3. **Junction-полнота проверяется структурно, не семантически.** Шаг 4 видит, что junction-claim *есть*; то, что он связывает именно нужные Post/Pre — обязанность компиляции interfaces→claims (U) и предмет теоремы A3. **До A3 формат несёт композицию синтаксически.**
4. **Roots-минимализм против полноты.** Blind-spot (Corollary 1) наследуется: гарантировано ровно то, что в roots. Trust-manifest обязан содержать поле `coverage indicators` (Def 6 whitepaper) с явной пометкой «эвристика».
5. **Остаточный риск N сохраняется** (TCG-001 §2): формат гарантирует, что nav/ вне формальной цепочки; не гарантирует, что усталый проверяющий не поверит красивому тексту вместо спуска к roots. Социотехнический риск.

## 9. Новые/изменённые посылки для трудовой базы
 
| Посылка | Формулировка | Статус |
|---|---|---|
| **Trusted-claim discipline** (заменяет обсуждавшуюся «summary adequacy») | Claim, помеченный trusted при проверке узла, доказан в узле-ребёнке того же сертификата, и DAG ацикличен | machine-checkable (шаг 4) |
| **Assumption 4 (усилена)** | Якорь = hash(deployed runtime bytecode) + hash(canonical claim), не AST/источник | machine-checkable (шаг 2) |
| **Assumption 1 (уточнена)** | Семантика vendored в бандл, а не пиннована ссылкой | vendored (шаг 3) |
| **Assumption 7 (уточнена, D1)** | H валидирует **roots**, не каждый φᵢ; факт валидации датирован и подписан в oracle-record | verifier-action-required (шаг 6) |

## 10. Открытое (переходит в план)
 
1. **Формат claims:** предполагается K spec-module синтаксис как каноническая форма v1; стабильность синтаксиса между релизами K **не проверена** — возможно, канонической формой должен быть **Kore**, а не K-frontend. → задача C1-класса.
2. **`Effᵢ` — задел без семантики.** До H-I/A3 это документация, не гарантия. **Помечать в trust-manifest как `not yet load-bearing`.**
3. **Выразимость Trace/Exit в claim-форме.** Claims — reachability (init ⇒ final); trace-инварианты потребуют либо инструментирования конфигурации (ghost-ячейки), либо all-path операторов. Технический узел, не проверен.
4. **Гранулярность claims per loop.** Один claim на внешнюю функцию — практика KEVM; наш loop может не совпадать с функцией. Соответствие loop ↔ множество claims не проработано.
5. **Схема идентичности H** для oracle-record (ключи, кто выпускает) — продуктовый вопрос, не проработан.
6. **Не проверено кодом:** поведение `--trusted` на текущей версии kprove (kore-issue датирован 2019, механика могла эволюционировать); поведение CSE при промахе покрытия summary (Unknown / fallback / молчаливое принятие).
7. **Не подтверждено:** conformance-валидация Certora TAC-пайплайна и hevm против ethereum/tests; выразимость Trace/Exit в Act и CVL; зрелость Act для нетривиальных контрактов.
8. **Компромисс, не отмеченный в TCG-001:** `Postᵢ` минимально достаточный (§3) конфликтует с покрытием: слабый Pre расширяет покрытие, но ослабляет гарантию; сильный — сужает покрытие и роняет вызывающего в полное исполнение.

## 11. Итог
 
- **A1 закрыт:** доказательство на всю цепочку = **множество root-claims** + claim-DAG с trusted-дисциплиной; композиционная soundness сводится к (ацикличность + замкнутость + per-node Accept), но **формально доказывается в A3**.
- **A2 закрыт:** форма — **TCG-бандл** (§5), протокол — §6, эволюция — §7.
- **Суждение о стеке зафиксировано:** borrow the semantics, build the certificate, commoditize the prover.
- **Следующий по зависимостям — A3** (теорема: «валидный бандл ⟹ композиционная soundness roots»).
