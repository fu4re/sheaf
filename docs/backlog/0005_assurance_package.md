# Task 0003 — Session Artifact Format (assurance package) — pilot integration

- **Дата:** 2026-06-25 · **Тип:** инженерная задача (pilot, реальные пайплайны)
- **Опирается на:** Finding 0001 (генерация), Finding 0002 (солвер-судья), T2 (семантика claim'а + trusted-base-ledger)
- **TL;DR:** сессия верификации должна выпускать **один самодостаточный пакет**, который
  третья сторона (заказчик / аудитор / CI) перепроверяет «в обратную сторону» без доступа
  к сессии. Ядро пакета — assurance-граф claim'ов, замкнутый на Lean-проверенные теоремы
  и явно перечисленные допущения. Цель пилота — собрать формат на существующих пайплайнах
  (cvc5 + Lean) и проверить, что обратная проверка работает руками чужого человека.

---

## Зачем (одно предложение)

Продукт = эпистемическое утверждение «proved». Если артефакт не несёт точную формулу
claim'а + ограниченный человекочитаемый список допущений, перепроверяемый независимо —
продавать нечего (это и есть блокер T2). Эта задача делает артефакт.

---

## Что выпускает сессия (определение готового пакета)

Каталог из шести частей. Иерархия по принципу «без чего рушится эпистемика — ядро;
без чего теряется удобство — обёртка».

| Слой | Файл(ы) | Роль | В trusted base чего |
|---|---|---|---|
| **Ядро** | `assurance_graph.yaml` | граф claim'ов, рёбра к листьям | claim'а |
| **Trusted base** | `trusted/ledger.yaml` | реестр ВСЕХ листьев (proven/assumed) | claim'а |
| **Evidence** | `evidence/lean/**`, `evidence/smt/**` | то, что граф цитирует; перепроверяемо | claim'а |
| **Линтер** | `verify_package.py` | мех. проверка замкнутости/ацикличности | — (мета) |
| **Обёртка** | `provenance.intoto.json` (+DSSE) | происхождение, не подмена | поставки, НЕ claim'а |
| **Вид** | `view/AUDIT.md` (+GSN-картинка) | автоген проекция для человека | — (проекция) |

**Инвариант пакета (machine-checked):** ни один claim не ссылается на лист, которого нет
в `ledger.yaml`. Граф ацикличен. Каждый `proven` несёт evidence. Линтер обязан падать,
если допущение спрятано (демонстрация падения — часть приёмки).

## Структура claim-записи (нормативная)

Каждый claim в `assurance_graph.yaml` несёт:

- `id` — стабильный, для линковки
- `human` — одна строка на естественном языке
- `formal` — машиночитаемая формула (SMT-LIB-выражение), НЕ проза
- `shape` — `stateless` / `quantified-over-mapping` / `temporal-2state` (таксономия из F0001)
- `verdict` — `proven` / `refuted` / `inconclusive` (последние два НЕ прячем)
- `engine` — солвер + версия + режим (+ `lean-smt reconstruction` если есть)
- `evidence` — `{smt_query, lean_proof, reproduce}` или `{witness}` для refuted
- `depends_on[]` — рёбра, каждое: `{kind, ref, status, human}`, где
  `status ∈ {proven, assumed}`. `proven` = идём по ребру дальше; `assumed` = лист, стоп.

## Структура trusted-base-ledger (нормативная)

- `lean_theorems[]` — `{id, statement_human, statement_formal, file, theorem_name, build_status, status}`
- `assumptions[]` — `{id, statement_human, statement_formal, why_assumed, risk_if_false, status}`
- `harness_faithfulness[]` — `{target, claim, evidence, evidence_ref, status}`
  ← самое слабое звено (модель ↔ байткод). Видимое, не спрятанное. `lean_proven` / `diff_fuzz` / `unverified`.

## Scope пилота

### In scope
1. **Один реальный контракт** на существующем пайплайне (кандидат: ERC-4626-микровол или
   self-contained как Vat-подмножество; НЕ bridges).
2. **Сборка пакета end-to-end:** агент генерит claim'ы (F0001) → cvc5 судит (F0002) →
   результат + Lean-мост укладываются в формат выше.
3. **Lean как носитель доверия:** минимум 1 claim замкнут на реально компилирующуюся
   Lean-теорему (`lake build` проходит в CI — в отличие от пилота-черновика, где не гонялся).
4. **lean-smt мост:** на ≥1 claim'е снять лист `solver_trust`, заменив Lean-реконструкцией.
   Замерить, что реконструкция реально проходит ядром (а не «должна бы»).
5. **Линтер** `verify_package.py`: замкнутость + ацикличность + «падает на спрятанном допущении».
6. **Автоген `view/AUDIT.md`** из ядра (не параллельный руками документ).
7. **Обратная проверка чужими руками:** разработчик, НЕ участвовавший в сессии, проходит
   пакет сверху вниз и выносит вердикт по листьям. Замерить: сколько времени, где споткнулся.

### Out of scope (явно, чтобы не расползлось)
- Полный SACM-метамодель (XMI/UML). Берём **лёгкий профиль** SACM в YAML, не стандарт целиком.
- Carcara/Alethe как дефолт — только опциональный запасной путь, если lean-smt не вытянул фрагмент.
- TPTP, PROV как отдельный слой, SLSA как отдельный стандарт — схлопнуты в in-toto-предикат.
- UI/продуктовая обёртка. Пакет = файлы в каталоге + CLI-линтер. Никакого фронта.
- Автосинтез proof harness (это отдельный moat-трек, не эта задача).

## Критерии приёмки (Definition of Done)

1. **Пакет существует** для 1 реального контракта, проходит `verify_package.py` → WELL-FORMED.
2. **Lean реально компилируется:** `lake build` в CI зелёный; `build_status` в ledger не врёт.
3. **lean-smt снимает ≥1 `solver_trust`-лист:** доказано, что claim перепроверен ядром, не солвером.
4. **Линтер ловит спрятанное допущение:** демо — убрать лист из ledger → INVALID + exit 1.
5. **Честный refuted в пакете:** ≥1 над-claim агента опровергнут с witness (как C3 в примере).
6. **Faithfulness видим:** harness ↔ контракт замерен (diff-fuzz N прогонов) ИЛИ помечен `unverified`.
7. **Slepая обратная проверка:** чужой разработчик за ≤30 мин доходит до листьев и выносит
   решение, опираясь ТОЛЬКО на пакет (без вопросов автору сессии). Лог его прохода приложен.

## Риски / открытые вопросы (честно)

- **lean-smt молод (2025), покрытие фрагментов неполное.** Часть целей с нелинейной
  арифметикой (`rayMul`/`mulDiv`) он может не реконструировать → останется `solver_trust`
  или ручной Lean. Замерить, какая доля целей реально проходит мост.
- **Faithfulness harness↔байткод не закрывается ни Lean, ни in-toto.** Для пилота — diff-fuzz;
  для общего случая остаётся `assumed`. Это известный moat, не дефект задачи.
- **Профиль SACM — наш, не стандарт.** Узнаваемость имени (ISO 15026/OMG) частичная.
  Решить на пилоте: достаточно ли «опирается на SACM» для продажи, или нужен полный экспорт.
- **Стоимость на claim.** F0001/F0002 дали ~$0.16–0.20 за генерацию+суд. Замерить полную
  стоимость СБОРКИ ПАКЕТА (вкл. Lean-мост) на claim — это юнит-экономика продукта.

Если слепая проверка прошла и юнит-стоимость приемлема → формат становится **стандартным
