# Task 0013 — нейро-провер для Lean-разрядки ghost-аксиом (эмпирическая оценка)

- **Дата:** 2026-06-28 · **Тип:** ресерч-задача (e2e idea-validation → numbered Finding)
- **Опирается на:** [план tcg CLI](../plans/adr-federated-parrot.md) (§ Q3) · ADR-0003 (untrusted-генератор + trusted-чекер) · Finding 0002/0007 (Lean trusted-base) · Task 0006 (neural_lean_seam)
- **Зависит от:** 0006 (seam-данные) · **Разблокирует:** — (опциональное liveness-расширение, НЕ soundness-блокер MVP)
- **TL;DR:** проверить эмпирически, могут ли нейро-провер'ы (Pythagoras-32B, Goedel-V2, DeepSeek-V2, Kimina) разряжать **наши** ghost-аксиомы в Lean — выдавая терм, который **проверяет ядро Lean** (ноль добавленного доверия). Паттерн архитектурно одобрен; вопрос — способность на нашем домене (не олимпиадная математика).

## Зачем (одно предложение)

Ручная Lean-разрядка ghost-аксиом — bottleneck; нейро-провер как **untrusted-генератор за ядром Lean** автоматизирует её *без добавления допущений* (кривой proof отвергается ядром) — но способность на наших definition-heavy леммах неизмерена, а упор у нас в «максимальную точность без неявных допущений».

## Что проверяем (анкерные леммы из `AaveArith/Basic.lean`)

- **L1 (easy, Mathlib-shaped):** `mulDiv_le_left` (`y≤d → x*y/d ≤ x`), `mulDiv_mul_le` — почти наверняка one-shot.
- **L2 (trivial):** `ar_delta` (`(Art+dart)*rate = Art*rate + dart*rate`, дистрибутивность).
- **L3 (hard, project-specific):** `transfer_sum_preserved` — Σ по `Finset` под двойным `Function.update`, через `Finset.sum_update_of_mem`+`omega`. **Реальный стресс-тест** «олимпиадный провер vs наша доменная лемма».

Все три — в терминах **наших** defs из нашего lake-проекта, не self-contained miniF2F-строк.

## Setup (house-style ресерч)

1. Взять `neural_lean_seam`-аксиому(ы) из `setup_report.json` (Task 0006).
2. Прогнать ≥2 провер'а (кандидаты: **Pythagoras-32B** [новейший, 89.8% miniF2F], **Goedel-V2-8B/32B** [self-correct через Lean-фидбек]; open weights, kernel-checkable).
3. **Критично:** дропнуть вывод провер'а в `cycle/trusted/proofs/aave_arith` и прогнать `lake build` против **нашего пиннутого тулчейна** (Lean 4.31.0 + Mathlib v4.31.0) — proof засчитывается ТОЛЬКО если ядро принимает.
4. Замерить pass/fail по L1/L2/L3, версионную совместимость тактик, latency/cost.

## Definition of Done

1. **Trust-model подтверждён:** для каждого провер'а зафиксировано, что он эмитит kernel-checkable Lean-терм (а не голый «proved»); провер, дающий только вердикт без артефакта — **дисквалифицирован** (добавил бы неявное допущение).
2. **Замер на L1/L2/L3:** таблица pass@k по нашим аксиомам, с реальным `lake build` (ядро), не «должно бы».
3. **Версионная совместимость:** зафиксировано, билдится ли вывод против Lean 4.31.0/Mathlib v4.31.0 (риск рассинхрона тактик).
4. **Честный негатив приветствуется:** если L3 (Finset) не берётся — записать прямо (ценный результат: граница «олимпиадный провер vs наш домен»).
5. **Numbered Finding** (следующий свободный, ~0008) в house-style: Setup-таблица, результат по L1/L2/L3, honest caveats, вывод о выборе провер'а.

## Артефакт (проверяемый отдельно)

`docs/findings/00NN_neural_lean_prover_<...>.md` + Lean-файлы выводов провер'ов в `docs/findings/artifacts/`. Проверяется независимо: перезапуск `lake build` на приложенных proof-термах воспроизводит kernel-вердикт; ни одна аксиома не помечена `proven` без проходящего ядром терма.

## Риски / открытые

- Провер'ы натренированы на miniF2F (олимпиада); перенос на DeFi-fixed-point **не гарантирован** — это и есть гипотеза задачи.
- Версии Mathlib: тактики ломаются между релизами → может потребоваться апдейт нашего пина или ручная починка вывода (которую ядро всё равно проверит).
- **Не soundness-блокер:** MVP едет на ручных Lean-аксиомах (уже работают, F0002/0007); это liveness/cost-ускорение.
