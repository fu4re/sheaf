**Что реально видно у Certora (проверено по репо, не по памяти)**

AutoProver — открытый (GPL-3.0, Python) многоагентный пайплайн: по project root, главному контракту и design-документу он анализирует компоненты системы, формулирует свойства, генерирует CVL-спеки и гоняет Certora Prover в цикле с ревизией провалившихся спек. Полезные для нас паттерны реализации:

1. **Headless-first.** Два entry point: Textual-TUI и headless console; console — для CI и логирования. UI — тонкая обёртка над тем же пайплайном.
2. **Всё — файловые артефакты в дереве проекта.** Выход пишется в `certora/`: specs, per-spec конфиги, и метаданные `properties.json` (формулировки свойств), `property_rules.json` (маппинг свойство→правила), `commentary.md` (LLM-комментарий). Их `properties.json` ≈ наш `interfaces.json`; `property_rules.json` ≈ наш маппинг interface→claims (узел C8); `commentary.md` ≈ наш `nav/report.md` — с той разницей, что у них он не отделён от доверия.
3. **Фазовый конвейер с чекпойнтами и кэшем.** Фазы: system analysis → harness setup (AutoSetup, compilation config, классификация внешних контрактов) → summaries → структурные инварианты → per-component извлечение свойств (параллельно) → per-component генерация CVL + prover-in-loop (параллельно, max-concurrent); Postgres-базы под checkpoints для резюмирования, память агентов и audit_db с историей исполнения и результатами prover'а; кэш по SHA-256 от (project root, design doc, contract path, name) — у нас это бесплатно даёт контент-адресация claims.
4. **Всё пиннуется в контейнере.** Docker-образ с Python, JRE, всеми версиями solc, RAG и Postgres; единственное требование к хосту — Docker. Совпадает с нашим решением «контейнер как удобство вне trust-корня».

Ключевые расхождения, которые фаза 1 обязана сохранить: у них Accept prover'а терминален (нет freeze/verify-разделения, нет бандла, нет replay третьим лицом); summaries — Aasm без обязательной перепроверки; H-гейта нет (design doc даже автообнаруживается агентом); композиционной гарантии между компонентами нет. Ровно эти четыре пункта — наши вклады №1–3, и они же — содержание фазы 1.

# Фаза 1 — CLI v0, e2e

## Критерий приёмки (демо-сценарий, определяет «работает e2e»)

На машине A: мини-экземпляр (Deposit.sol: `deposit` + `withdraw`, форма withdraw зафиксирована по Г2-развилке) → `tcg init` → интерфейсы → prove обоих loop'ов → junction + compat → `tcg freeze` → каталог `bundle/`.

На чистой машине B (только Docker): `git clone bundle && tcg verify bundle/` → шаги 1–5 протокола зелёные → `tcg roots bundle/` печатает roots. Это материализованный вклад №3.

Обязательные **негативные контроли** (без них зелёное не доказано):
- подмена байта в `runtime.bin` → отказ на шаге 2;
- удаление доказанного child-claim → отказ на шаге 4 (замкнутость);
- инъекция заведомо ложной trusted-леммы → отказ на шаге 5 (это конфиг (c) из C9-Q1 — зафиксированное обоснование несущей роли replay);
- `rm -rf nav/` → verify проходит без изменений + grep по trust-замыканию не находит ссылок в `nav/` (механическая проверка критерия N);
- Unknown на replay → отказ сертификата (консервативность), с retry-политикой из `toolchain.lock`.

## Команды CLI

```
tcg init                  # scaffold + toolchain.lock (kontrol 1.0.255 / K v7.1.337 /
                          #   KEVM 1.0.678) + vendored fork (theory/patches/*.diff)
tcg loop new <name>       # workspace loop'а
tcg iface set <loop>      # (Pre, Post, Exit, Foot_r/w, Rely, Guar) → interfaces.json
tcg compile-claims <loop> # U-компилятор iface→canonical claim (K spec-module,
                          #   явный [all-path], ghost/wf-дисциплина) + round-trip print-back
tcg approve               # акт H: oracle-record, подпись по текущим хешам roots (шаг 4.5)
tcg prove <loop|junction> # kprove, дети-как-trusted; результат Accept/Refute/Unknown(a|b|c)
tcg junction <i> <j>      # consequence-claim Post_i ⟹ Pre_j
tcg compat <i> <j>        # Guar_j ⟹ Rely_i (+ env-узел) при пересечении footprint
tcg graph check           # шаг 4: ацикличность trusted-lemma-подграфа, замкнутость,
                          #   типизация рёбер, [all-path], guar-узел на loop, roots
tcg freeze                # сборка бандла, хеш-дерево, MANIFEST
tcg verify <bundle>       # шаги 1–5 отдельным процессом: целостность → идентичность →
                          #   теория/layout-перепроверка → граф → топологический replay
tcg roots <bundle>        # шаг 6: рендер roots для человека
```

`freeze` и `verify` — принципиально разные бинарные пути: verify не читает workspace, только бандл (иначе транзитивность доверия — декларация, а не конструкция).

## Конвейер e2e (аналог их Phase 0–5, с обращённым доверием)

| # | Стадия | Аналог у AutoProver | Наше отличие |
|---|---|---|---|
| P0 | Build: пиннованный solc, `runtime.bin`, storage-layout + **layout-перепроверка против байткода** (Aasm-леджер) | Harness Setup / AutoSetup | layout — не молчаливый вход, а перепроверяемая запись `annotations.json` |
| P1 | `environment.json`: форк, chainid, класс calldata | compilation config | часть trust-manifest, не тулинг-конфиг |
| P2 | Интерфейсы per loop → компиляция в canonical claims | properties.json → CVL | компилятор U (H-H): валидируется claim, не IR; round-trip обязателен |
| P3 | Per-loop prove, дети-как-trusted, параллельно по DAG | per-component prover-in-loop | Accept не терминален — он вход в бандл; Unknown классифицируется (a/b/c) |
| P4 | Junction (consequence) + compat (Guar⟹Rely) + env-узел | **нет аналога** | это и есть вклад №1; типизация рёбер trusted-lemma/consequence/compat |
| P5 | Freeze: бандл по спеке TCG-003 §5.2 + леджер патчей r8 §7 (root-assembly, роли guar/frame/compat/env, три ghost-diff'а) | **нет аналога** | `nav/` вне хеш-дерева; oracle-record |
| P6 | Verify на чистой машине | **нет аналога** (их результат = отчёт) | вклад №3 |
| P7 (1b, опционально) | U-контур: LLM предлагает спеку/инвариант, дешёвые рефутеры (SMTChecker/Halmos) до kprove, Refute-реплей на конкретном клиенте до feedback | Phase 4–5 агенты + feedback loop | генерация **не на критическом пути приёмки**: sheaf-инсайт — «ничего нового доказывать не надо, нужно собрать» |

Спеки в 1a пишутся руками (перенос из спайков T1–T3). Это осознанно: приёмка фазы 1 — сборка и replay, а не качество генератора; их же паттерн подтверждает, что генерация подключается к готовому конвейеру фазой, не переделкой ядра.

## Модель данных на диске

Workspace (`.tcg/`): состояние loop'ов (state machine `Draft → Compiled → Proving → Accepted/Refuted/Unknown/Stale`), очередь prove-задач, `nav/session/` provenance (аналог их audit_db, но файлами — Postgres в v0 не нужен). Резюмируемость — через контент-адресацию: claim с тем же хешем и тем же множеством trusted-детей не перепрогоняется (их `--cache-ns`, но с честным ключом).

Bundle — строго по TCG-003 §5.2 с применённым леджером патчей PLAN r8 §7. **Предусловие фазы: применить леджер в единый bundle-spec v1 документ** — это уже помечено в базе как неисполненное.

## Риски, названные заранее

- **Интеграционная граница Г1/T1-Q2a:** raw kprove не авто-конфигурирует целый вызов; v0-claims живут на уровне, отработанном в спайках, C10 (полное байткод-замыкание) вне scope. MANIFEST обязан честно декларировать тип evidence на узел — формат это уже допускает.
- **C6-нестабильность K-синтаксиса** между релизами — покрыта пиннингом; развилка K-frontend vs Kore остаётся открытой, print-back её страхует.
- **Недетерминизм солверов на replay** — Unknown = отказ (консервативно), retry-политика в `toolchain.lock`; это главный довод за v2-evidence, но скелет бандла переход переживает.
- **Phantom-return** — граница монитора, строка в trust-manifest, фикс (C11) вне фазы 1.

**Uncertainty:** внутренности оркестрации AutoProver (composer/graphcore) я читал только по README — глубже смотреть имеет смысл выборочно (их state machine ревизии спек и структура feedback после провала prover'а) при постройке 1b. Их продуктовый клейм «AutoProver проверяет, что intent на естественном языке транслируется в то, что код действительно делает» — это ровно тот зазор, который TCG принципиально не закрывает автоматикой, а выносит в H (Assumption 7): в фазе 1 это `tcg approve` + oracle-record, и в этом месте копировать их нельзя.

Следующий шаг по готовности: разложить п.1 (bundle-spec v1) — могу собрать консолидированный документ из TCG-003 §5.2 + леджера r8 §7 как отдельный артефакт.
