# ADR-0003 — Trusted Code Generation (TCG) module

- **Status:** Accepted
- **Date:** 2026-06-27
- **Scope:** End-to-end specification-conditioned code-generation cycle
- **Supersedes:** —
- **Related:** TCG whitepaper (formal framework); subsequent ADRs will bind concrete tools (verifier backend, formalizer, generator) to the roles defined here.

---

## 1. Context

We are building an end-to-end (e2e) cycle that turns informal human intent into deployed contract bytecode **with a formal correctness guarantee**. The generative component is a language model. The problem is that a language-model output is *plausible*, not *proven*: it is a high-likelihood sample, carrying neither justification nor a guarantee of truth.

Two naive architectures are both wrong for us:

1. **Trust the generator.** Make the model "more reliable" (better prompts, self-critique, more reasoning) and ship what it emits. No amount of generative competence converts a sample into a proof — the two are different categories. This gives us a confident system that can still be silently wrong, which for value-custodying contracts is the worst failure mode.
2. **One monolithic verified pipeline.** Try to prove the *whole* path from natural language to bytecode correct. This is impossible in principle: natural language has no formal semantics, so "the translation is correct" is not even a well-defined predicate. There is nothing to prove against on the natural-language side.

We need a third architecture that (a) lets the model be as creative — and as wrong — as it likes, (b) still emits only artifacts that carry a real guarantee, and (c) is honest about the one place where no formal guarantee is possible.

This ADR records that decision and defines the **contour** of the module the e2e cycle must implement. It is deliberately **tool-agnostic**: it fixes roles and their trust status, not a specific verifier, formalizer, or model. Concrete tool choices are downstream ADRs.

---

## 2. Decision

We adopt the **Trusted Code Generation (TCG)** architecture: a hard trust boundary between an **untrusted generation region** and a **trusted, formal verification core**, with the generative model permanently on the untrusted side.

The governing principle, which every implementation decision must preserve:

> **System soundness is invariant to the capabilities of the generative model.** Any artifact the system accepts is verified against a formal specification; any artifact that cannot be verified is rejected. The model may be arbitrary or adversarial without breaking this guarantee.

### 2.1 The module and its components (roles)

The TCG module is a composition of five roles. Each carries a **trust status** that is part of its contract:

- `U` — **untrusted**: may behave arbitrarily, including adversarially. Its output is always checked downstream.
- `T` — **trusted-formal**: part of the formal core; its correctness is assumed and its failure breaks the guarantee.
- `T*` — **non-formal trusted**: a trusted *assumption* (a human), not a verification component. In the trusted base but **not** in the formal core.

| Role | Name | Trust | Responsibility |
|------|------|-------|----------------|
| `F` | Formalizer | `U` | Turn intent into a candidate formal specification `φ`, or abstain. |
| `H` | Human oracle | `T*` | Validate that `φ` expresses the intent; declare `φ` the correctness oracle. |
| `G` | Generator | `U` | Produce a candidate bytecode artifact from `φ` (and prior counterexamples). "Vibe coding." |
| `I` | Synthesizer | `U` | Produce the annotations and certificate the checker needs (loop invariants, etc.). |
| `K` | Checker | `T` | Mechanically decide whether the artifact satisfies `φ`. The only acceptance gate. |

The **formal trusted core** is exactly `{ K, the proof checker it uses, the formal machine semantics }`. `H` is a trusted assumption alongside the core, not inside it. `F`, `G`, `I` are untrusted.

### 2.2 What `φ` is

`φ` is **not** a single postcondition. It is a tuple over full machine configurations:

```
φ = (Pre, Trace, Post, Exit)
```

- `Pre` — predicate on the entry configuration.
- `Trace` — predicate over the execution trace (a trace invariant). Expresses reentrancy discipline, callback rules, event/log obligations — anything about the *sequence*, not just the endpoint.
- `Post` — predicate on the terminal configuration.
- `Exit` — the set of admissible terminating statuses (e.g. successful-halt / revert / out-of-gas / exceptional-halt).

A terminal-only partial-correctness claim is the special case `Trace = true`, `Exit = {halt}`. The implementation MUST support the full tuple; degrading to terminal-only silently is a defect, because trace-sensitive properties (reentrancy, revert behavior, emitted events) are exactly the high-value ones.

### 2.3 The checker is two ideas, not one

A critical implementation rule that the e2e cycle must encode explicitly: **operational acceptance and semantic truth are different things, bridged by an assumption.**

- **Operational acceptance** (`K` says Accept): a *decidable, syntactic* procedure — the checker validates a certificate as discharging all proof obligations. It makes no reference to truth.
- **Semantic truth**: the statement that, over the formal machine semantics, every terminating trace of the artifact from `Pre` satisfies `φ`.
- **The bridge**: an assumption that the checker is sound — *if it accepts, the semantic claim holds*.

Implementations MUST NOT define "accepted" as "true." Acceptance is what the checker mechanically does; truth is what we get *only* via the soundness assumption. Collapsing them turns the whole guarantee into a tautology and hides the one assumption (checker soundness) that actually carries weight.

### 2.4 Checker result is structured

`K` returns one of three outcomes — never a bare boolean:

```
Result = Accept(certificate)
       | Refute(counterexample)
       | Unknown(reason)        // timeout, solver incompleteness, ...
```

- `Accept` → done; emit `(artifact, φ)`.
- `Refute` → carries a counterexample; **may** be fed back to `G`.
- `Unknown` → carries **no** counterexample; MUST be treated as non-acceptance, and MUST NOT be fed back as if it were a refutation.

`Refute` and `Unknown` are both non-acceptance, but they are operationally different: only `Refute` drives the refinement loop. Conflating them (e.g. "anything that isn't Accept is a counterexample") is a defect.

### 2.5 The e2e contour (the loop)

```
intent n
  │
  ▼
[F] formalize ───► φ?  ──(⊥)──► abstain: ⊥_spec        (no spec produced)
  │ φ
  ▼
[H] validate φ vs n ──(reject)──► abstain: ⊥_spec      (human declined)
  │ ok  (φ is now frozen as the correctness oracle)
  ▼
┌─────────────── generate–verify–refute loop, k = 1..K_max ───────────────┐
│                                                                          │
│  [G] generate artifact b_k  (conditioned on φ and counterexamples<k)     │
│         │ b_k                                                            │
│         ▼                                                                │
│  [I] synthesize annotations + certificate                                │
│         │                                                                │
│         ▼                                                                │
│  [K] check (b_k, φ, annotations, certificate)                            │
│         ├─ Accept(cert) ──────────────► return (b_k, φ)   ✅ verified     │
│         ├─ Refute(ce)   ── feed ce back into G, continue                  │
│         └─ Unknown(...)  ── continue, no feedback                         │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
  │ budget exhausted, no Accept
  ▼
⊥_gen   (failed to synthesize an accepted artifact)
```

Three terminal outcomes, **all safe**:
- `⊥_spec` — abstained at the specification stage.
- `⊥_gen` — could not synthesize an accepted artifact within budget.
- `(b, φ)` — an accepted, verified pair.

The system **never** emits a non-accepted artifact labeled as accepted. That property holds by construction, before any environmental assumption — it is the floor the implementation must never breach.

### 2.6 Trust boundary — where everything to the left is disposable

```
        UNTRUSTED region                    │   TRUSTED core      │  Trusted assumption
  ┌──────────────────────────────┐          │  ┌──────────────┐   │  ┌──────────┐
  │  F  ──►  G  ──►  I            │ ───────► │  │  K (checker) │   │  │  H       │
  │  (arbitrary / adversarial)   │          │  │  + proof chk │   │  │  (human) │
  └──────────────────────────────┘          │  │  + semantics │   │  └──────────┘
                                             │  └──────────────┘   │
       can be replaced wholesale             │   if it accepts,    │  closes the
       without affecting soundness           │   the claim holds   │  intent gap
```

Mental model for reviewers and implementers: **anything in the untrusted region can be swapped for an arbitrary or even malicious procedure and the soundness guarantee still holds.** Only liveness (whether we ever produce an accepted artifact) depends on the generation region. That asymmetry is the entire point of the architecture.

## 3. Invariants the implementation MUST hold

These are the non-negotiable contracts of the module. A change that violates any of them is not a tuning choice — it breaks the guarantee and requires a new ADR.

1. **The checker is the sole acceptance gate.** No artifact is emitted as verified except via `K = Accept`. No other component may mark an artifact accepted.
2. **The model is never trusted.** `F`, `G`, `I` outputs are always inputs to `K`, never axioms. Improving the model changes liveness/throughput, never soundness.
3. **Acceptance ≠ truth in code.** Operational acceptance, semantic truth, and the soundness bridge are represented as distinct concepts. The codebase must not let "accepted" stand in for "true."
4. **Unknown is rejection.** `Unknown`/timeout/solver-failure yields non-acceptance. Conservative by default; never an accept-on-doubt path.
5. **Refute ≠ Unknown.** Only `Refute` feeds the refinement loop. `Unknown` carries no counterexample and must not be replayed as one.
6. **`φ` is frozen after `H`.** Once the human validates `φ`, the loop verifies against *that* `φ`. The generator must not be allowed to weaken or rewrite the spec it is being checked against.
7. **Verified artifact = deployed artifact.** Whatever `K` verified must be bit-identical to what is deployed (account for constructor vs runtime forms). A mismatch here silently voids the guarantee.
8. **Annotations are checked or declared.** Annotations `I` produces are split: those the checker fully discharges as obligations vs. external facts (e.g. layout hints) that are *not* self-checking. The latter MUST be either eliminated or recorded explicitly in the trusted base — never silently believed.
9. **Specification parameters are pinned.** The fork/version and fee schedule the checker reasons under MUST match deployment, and be recorded with the verified pair.

## 4. Consequences

### 4.1 Positive

- **Soundness decoupled from model quality.** We can adopt a stronger or weaker generator, or a different model entirely, without re-arguing correctness. Model upgrades are liveness/cost improvements.
- **Honest failure modes.** The system abstains (`⊥_spec`, `⊥_gen`) rather than shipping unverified code. For value-custodying contracts, a clean abstention is the correct behavior.
- **Tool independence.** Because the contract is roles + trust status, the verifier backend, formalizer, and generator are swappable behind stable interfaces. This ADR survives those swaps.
- **Auditable trust base.** The set of things we trust is small and named: the checker, its proof checker, the machine semantics, the human's spec validation, and artifact identity. Everything else is checked.

### 4.2 Negative / accepted costs

- **The intent gap is irreducible and ours to own.** The correspondence between `φ` and the human's true intent is **not** provable — natural language has no formal semantics. We discharge it as an explicit human assumption (`H`), not as a guarantee. The product must surface `φ` to the human in a reviewable form; "the human approved `φ`" is a load-bearing step, not a formality.
- **Specification completeness is the real bottleneck.** Soundness says the artifact satisfies `φ`; it says nothing about properties *absent* from `φ`. Silence in the spec is a blind spot, not a safety guarantee. The hard, ongoing work is making `φ` complete — proposing candidate properties, surfacing unspecified paths — which the generative model can assist with *while remaining untrusted* (every proposed property is validated by `H` and checked by `K`).
- **Throughput depends on the untrusted side.** A weak generator means many loop iterations or frequent `⊥_gen`. Soundness is safe, but usefulness is not free; the generation region is where we invest for liveness.
- **The checker is a real dependency.** Its soundness, and the fidelity of the machine semantics to the real machine, are assumptions. Mitigations (small auditable certificate checker; cross-validation against a second semantics) are downstream engineering, not solved here.

### 4.3 Out of scope for this ADR

- Concrete choice of verifier backend, formalizer, generator, and how `H` reviews `φ` — separate ADRs.
- The coverage/completeness *metric* for `φ` (an operational heuristic, explicitly not a completeness guarantee) — its own design note.
- Negative-space evaluation (deliberately buggy contracts, mutated contracts, weakened specs, fork/artifact-mismatch tests) — the test-plan document.

## 5. Acceptance checklist for the e2e implementation

An implementation conforms to this ADR if and only if:

- [ ] The only path to an "accepted" artifact runs through `K = Accept`.
- [ ] `F`, `G`, `I` are structurally untrusted: their outputs are inputs to `K`, never trusted facts.
- [ ] `φ` is the `(Pre, Trace, Post, Exit)` tuple, not a terminal postcondition alone.
- [ ] `K` returns structured `Accept | Refute | Unknown`; `Unknown` is treated as rejection; only `Refute` feeds the loop.
- [ ] `φ` is frozen after `H = ok` and cannot be rewritten by `G` during the loop.
- [ ] Verified bytecode is proven bit-identical to deployed bytecode.
- [ ] Annotations are partitioned into checked-obligations vs. declared-assumptions; no silent trust.
- [ ] Fork/version and fee schedule are pinned and recorded with each verified pair.
- [ ] All three terminal outcomes (`⊥_spec`, `⊥_gen`, `(b, φ)`) are implemented and safe; no fourth "shipped but unverified" path exists.
